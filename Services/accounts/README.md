# accounts — personal accounts in the security master

Python Layer 3 service (port **8774**) that keeps **MxAcctMGR's My Portfolio** in MxDataHUB's security master
(PostgreSQL schema `srm`, migration **V011**), so the sandboxed app needs no database credentials.

| Endpoint | What it does |
| --- | --- |
| `GET /securities?q=&kind=&offset=&limit=&sort=&dir=&facets=` | Search by ticker, name, ISIN or CUSIP; `kind` = `all`, `stocks`, `funds`, `bonds` (bond and other fixed-income funds); a page at a time (`limit` ≤ 500) with the `total`; `sort` = `relevance` (default), `ticker`, `name`, `type`, `sector`, `exchange`, `price`, `asOf`, `marketCap` and `dir` = `asc` / `desc`; column filters `ticker`, `name` (contains), `type`, `sector`, `exchange` (comma-separated, `(none)` for blanks), `priceMin`, `priceMax`, `priced` (1 / 0); `facets=1` adds each filterable column's values with counts. Every price here, in browse, account lots and month-end prices is in dollars (`srm.last_price` / `srm.fx_to_usd`, V021): a London or Toronto line is converted, never shown in pence as dollars |
| `GET /benchmarks` | Benchmarks with members and snapshot date |
| `GET /benchmarks/<code>/weights` | The latest weights with ticker, name, sector and asset class |
| `GET /accounts` | Personal accounts (`srm.v_personal_account`) |
| `GET /accounts/<code>` | An account — type, approach, benchmark, cash — with its open tax lots valued at the latest prices |
| `PUT /accounts/<code>` | Save the account as its next version (`{version, name, accountType, approach, benchmark, cash, settings, by, note, lots: [{securityId, acquired, quantity, costBasis, note}]}`). `version` is the version the edit was made from — 0 for a new account; when the account has moved on (saved elsewhere, or already exists) the answer is **409** with the current `version`, `updatedAt`, `updatedBy` and nothing changes. Rewrites today's holdings snapshot with `srm.sync_holdings_from_lots` and keeps the saved version whole in `srm.portfolio_version` (V022) |
| `GET /accounts/<code>/versions` | Every saved version, newest first: when, by whom, account fields, cash, lots and cost |
| `GET /accounts/<code>/decisions`, `POST` | A portfolio's decisions, newest first; POST `{title, rationale, category, decidedOn, by}` records one with the portfolio's version (append-only, V023) |
| `POST /accounts/<code>/duplicate` | A new portfolio `{code, name}` from this one's saved version (lots, cash, benchmark, settings), version 1, with a decision noting where it came from; 409 when the code exists |
| `GET /benchmarks/policy`, `/benchmarks/policy/<code>` | Policy benchmarks with their dated mixes |
| `PUT /benchmarks/policy/<code>` | Define a policy benchmark: `{name, mixes: [{effectiveFrom, components: [{ticker or securityId, weight}]}], by}`; each mix adds up to 1; replaces the earlier mixes, then has the srm-loader service write the snapshots (`policy-benchmarks`); 409 for a market benchmark's code |
| `POST /securities/resolve` | `{tickers}` → `{securities: {TICKER: security with its latest price}, unknown}`: the current U.S. listing, else any current listing (mutual funds) — Import Holdings |
| `POST /accounts/<code>/close`, `/reopen` | Close a portfolio (kept, not deleted) or open it again; `{version}` checked like a save |
| `POST /accounts/<code>/load-prices` | Asks srm-loader (8770) to run `srm.py load nasdaq-prices --symbols …` (Nasdaq.com, free, no key) for unpriced holdings |
| `GET /bank/accounts`, `PUT /bank/accounts/<code>` | Checking accounts (V027) with register, cleared and PNC balances; PUT `{name, institution, last4, openingDate, openingBalance}` creates or changes one (last four digits only, never the whole number) |
| `GET /bank/accounts/<code>/register` | The shared check register, oldest first with the running balance, and the bank's lines no entry matches |
| `POST /bank/accounts/<code>/transactions` | Add an entry `{date, kind (check, debit, deposit, transfer, fee, interest), checkNo, payeeId or payee, expenseAccountId, memo, amount, by}`; a check number already in the register is **409**; then matches the bank's lines |
| `PUT /bank/transactions/<id>` | Change an entry `{version, …, status (open, cleared, reconciled, void)}`: **409** when someone changed it since. Entries are voided, never deleted |
| `POST /bank/lines/<id>/accept`, `/match` | Add the bank's line to the register (cleared; its payee found by the bank's name for it, which is remembered), or match it to an entry `{txnId}` |
| `POST /bank/accounts/<code>/import` | Asks srm-loader (8770) to run `srm.py load pnc-bank` (the PNC downloads in the drop folders) and answers with the register |
| `GET /expense-accounts/<id>/usage`, `DELETE /expense-accounts/<id>?moveTo=&by=` | What files under an expense account (`uses`: card entries, checking entries, target accounts, cash-ledger lines, card categories; `inUse`, `spendingRule`), and taking one off: when anything files under it, `moveTo` (another account of the same kind) is required and all of it moves there first; its spending rule goes with it. `PUT /expense-accounts/<id>` refuses a name another account has (ignoring case), keeps the description it doesn't send, and answers with the account's `id` too |
| `GET /expense-accounts`, `PUT /expense-accounts/<id>`, `PUT /payees/<id>`, `PUT /payees/<id>/note` | Expense accounts with their payees, this year's totals (`yearTotal`) and every year's (`totalPaid`); create (id 0) or change an expense account or a payee (a target account: `{version, name, nickname, description, status (active / inactive / closed), reference (its identifier), institution, last4, expenseAccountId, defaultAmount, nextPaymentDate, nextPaymentAmount, logonUrl, userName, address1, address2, city, state, zipCode, phone, notes, bankNames, fundingSources (checking and / or card: the registers whose target lists offer it)}`, V033; version-checked; a change keeps what it doesn't send, and a name another target account has (in any case) is refused with 409, and the names an older MxAcctMGR sends — address, website, active — still work; never a password: MxAcctMGR keeps those in the Keychain; `/note` changes only the note the register shows on hover, V028) |
| `POST /cards/accounts/<code>/import` | `{filename, text}`: saves a card download in the card's drop folder and asks srm-loader (8770) to run `srm.py load card-downloads`, then answers with the register; with `preview: true`, saves nothing and answers what the file holds for the card (`preview`: what it is, its dates, lines new / read / read from the other format, the new lines by kind, those before the register starts, categories with no expense account, every line). A file that isn't a card download, or names another card, is refused (400) |
| `POST /expense-ledgers/<code>/entries/delete` | `{entries: [{id, version}], by}`: deletes those entries of the ledger for good, all or none — **409** when someone changed one since; takes off their Year-End Tax moves (`tax_assignment`), their spending tags go by cascade, and the card charges and checks they were linked to stay. Answers with the ledger's book. Voiding (`PUT /expense-entries/<id>` with `status: void`) keeps an entry on record instead |
| `GET /cards/accounts/<code>/removal`, `DELETE /cards/accounts/<code>?confirm=<code>&by=` | What removing a card would clean up (`removal`: entries, those entered here, lines, statements, the drop folder's files; the checking and cash-ledger entries linked to its entries and its checking target, which stay; `remembered`: the tags, Amazon matches, notes, tax-year moves and edited entries on its downloaded lines); DELETE first keeps what was made on its downloaded lines (`srm.remember_card_lines`, V049: re-attached by `srm.post_card_lines` when a card with the same last four digits reads them again), then removes it with its entries, lines, statements and its row in `srm.spending_source` — refused (400) without `confirm` set to its code — and moves its drop folder to the drop folder's `_removed/<CODE>-<date-time>/`, answering `removed` (with `rememberedLines`) and the cards left |
| `GET /cards/targets`, `POST /cards/targets` | The names card entries carry without a target account, as the card company gives them (entries, total, first and last date, kinds; `merchant` false for the card company's own lines); POST `{names, by}` makes each a target account with the card funding source, in the category its entries mostly have, and links those entries to it (a name an account already has just gains the card source) |
| `GET /secure-accounts`, `PUT /secure-accounts/<id>` | Secure accounts (`srm.secure_account`, V035: `secure.py`): the products and services held an account with — `{version, name, description, serviceUrl, serviceApi, status (active / inactive / closed), ownerUserName, paymentDate, paymentAmount, renewalDate, renewalAmount, renewalStatus (auto / renew / decline)}`; create (id 0) or change one, version-checked, a change keeping what it doesn't send, and a name another secure account has (in any case) refused with 409. Never a product key, service key or password: MxAcctMGR keeps those in the Keychain (a service key is the API key MxJobsMGR's subscriptions send; MxJobsMGR lists these accounts to pick one, and its Move Keys creates them with `by: MxJobsMGR`) |
| `GET /spending/setup`, `GET /spending/analysis?start=&end=&priorStart=&priorEnd=`, `PUT /spending/members/<id>`, `DELETE /spending/members/<id>`, `POST /spending/categories`, `PUT /spending/categories/<code>`, `GET /spending/categories/<code>/usage`, `DELETE /spending/categories/<code>?moveTo=`, `PUT /spending/category-order`, `POST /spending/drivers`, `PUT /spending/drivers/<code>`, `GET /spending/drivers/<code>/usage`, `DELETE /spending/drivers/<code>?moveTo=`, `PUT /spending/driver-order`, `PUT /spending/rules`, `PUT /spending/triggers/<id>`, `DELETE /spending/triggers/<id>`, `PUT /spending/tags/<source>/<entryId>`, `GET /spending/sources?start=&end=&priorStart=&priorEnd=`, `PUT /spending/sources/<source>/<code>` | Household spending attribution (V037, `spending.py`) for MxAcctMGR's Reporting ▸ Spending Analysis. `setup` returns the family (`{name, relation child / adult, birthYear, birthMonth, notes, active, version}`), the spending categories with what each covers, their CPI series and assumed inflation, the drivers (V047, `{code, title, help, effect, sortOrder}`: effect is what the driver's growth beyond inflation counts as — inflation, usage, lifecycle, behavior, one_time or taxes), the rules (`{expenseAccountId \| payeeId \| pattern, category, driver, memberId, notes}`; nothing set removes one; a `pattern` is statement text, V042, at least 3 characters, matched ignoring case against the payee, statement name and description — `id` with a pattern changes that rule's text; `PUT /spending/rules/<id>/link` `{address, text, hoverText, hoverRtf, title}` and `DELETE` save or take off a statement text rule's link, V043, as `/payees/<id>/link` does a target account's), and — for MxAcctMGR, not the family page — each target account's bank, last four digits, logon page, nickname, notes and link, the lifecycle triggers (`{name, category, kind recurring / replacement / peak / transition, ageFrom, ageTo, everyYears, annualCost, notes, active}`; id 0 adds one), and the expense accounts, target accounts and CPI series to pick from. Every change answers with the setup. Categories and drivers (V047): `POST` adds one (`{name, description, cpiSeries, assumedInflation}` / `{title, help, effect}`, with a `code` or one made from the name: letters and _, upper case for a category, lower for a driver; a new category goes before Other); `PUT` changes only the fields sent; `usage` gives the rules, tags (and a category's lifecycle triggers) that set it and the entries in it now; `DELETE` moves those to `moveTo` first — required for a category with triggers; without it, rules and tags lose the category or driver, and rules and tags left setting nothing are taken off; the `-order` endpoints take `{codes}`, every one in its new order. `analysis` returns every spending dollar of both periods (`srm.v_spending_entry`: source bank / card / ledger, entry id, date, register, payee, expense account, amount positive when spent, category, driver and member with where each came from — entry, target account, statement text or expense account — and `rulePattern`, the statement text rule it matches), each category's price change between the periods (`rate`, `basis` CPI or assumed, months compared) and each register's first and last dates. `analysis` leaves out the registers not included (V038). `sources` returns:
- each checking account, credit card and cash ledger: `included` (with who chose it and when); its loader, drop folders and the downloads there for it (path, size, modified); the line and register tables; its lines' count and dates; its last import (the `load_run` of its newest lines); its register's entries, dates, how many came from downloads, last edit; and its spending in both periods;
- every SRM table and view the analysis reads (`tables`: role, rows, newest data date, last change);
- Amazon's order export (`amazon`, V046; null before it or when the role may not read it): its drop folders and downloads, orders and items with their dates, its last `amazon_orders` run, the period's Amazon charges in the analysis and how many it matched (count and dollars), `afterExport` (Amazon charges after its last order, unmatched: a newer export is due), and the period's `unmatchedCharges` and `unmatchedShipments` (shipped, not cancelled, no charge paid them);
- the latest `pnc_bank`, `card_downloads`, `amazon_orders` and `fred_yields` runs.

`POST /spending/amazon/load?start=&end=…` runs `srm.py load amazon-orders` through srm-loader (8770, `SRM_LOADER_URL` for a test one) and answers with the sources; with `{filename, data}` (the file in base64: Amazon's zip, or a `Retail.OrderHistory` CSV) it first saves it in the export's first drop folder, refusing a file that holds no order history. In `analysis`, an Amazon charge or credit matched to its order (`srm.v_amazon_charge`) carries `amazonOrders`, `amazonItems` `[{name, asin, quantity, amount, orderId, orderedAt}]` and `amazonMatchedBy` (amazon-orders: the export, by amount and date; amazon-lookup: Amazon's Transactions list), when the role may read the view.

MxAcctMGR's Amazon Order Lookup: `GET /spending/amazon/known?ids=A,B` answers which of these orders are kept (`{known: [{orderId, origin, items}]}`), so it reads only the others' pages; `POST /spending/amazon/attach` `{charges: [{source card | bank, entryId, orderIds}], orders: [{orderId, orderedAt, total, payment, items: [{name, asin, quantity, price}]}], by}` keeps each order its page gave (origin `order page`; an order read from the export stays as it is) and gives each charge the orders Amazon's Transactions list names (`how` transaction, `matched_by` amazon-lookup) in place of what it had, answering `{entries}`; `POST /spending/amazon/unlink/<source>/<entryId>` takes a charge's orders off for good (an `unlinked` row: the export doesn't match it again; the lookup can) and answers `{entry}`. Order numbers must look like Amazon's (`113-1234567-1234567`, `D01-…`).

PUT `{included, by}` includes or leaves out a register and answers with the sources. `GET /spending/sources/<source>/<code>/links` says what disconnecting it would undo (`links`: card payments linked to checks, cash-ledger entries linked to charges or checks, each with its count; `kept`: links kept from a disconnect). `POST /spending/sources/<source>/<code>/disconnect` `{by}` (V049) leaves it out of the analysis with its register kept, undoes those links and keeps them in `srm.source_link`; the payment and funding matches and the overlap finder leave it alone. `POST …/reconnect` `{by}` brings it back and puts each kept link back where both sides are still there and free, answering the sources and `reconnected {code, restored, skipped}`. A checking account's source has no drop folders, downloads or loader: its register is entered by hand. `GET /spending/feedback?author=&status=`, `POST /spending/feedback` `{author, kind (layout / number / rule / entry / idea / question), tab, section, category, entrySource, entryId, suggestion, message, context}` and `GET /spending/tax?year=` is Year-End Tax (V040). `GET /spending/overlaps` (Admin) lists the cash-ledger entries not linked to a card charge or check that match one — the same amount within a week, the charge or check linked to no entry — each `{entryId, version, ledger, date, vendor, description, amount, matches: [{source, txnId, register, txnDate, payee, days}]}`, up to three matches nearest first; `POST /spending/expense-account` `{entries: [{source, id}], expenseAccountId, fileFuture, targetName, by}` files card and check entries under another expense account; with `fileFuture` their target accounts are filed under it too, and entries with no target account get one (found by `targetName` or made, filed under it, its bank names their statement names) so future downloads post to it; cash-ledger entries are refused; answers with the setup, `changed` and `targetAccountId`. `POST /expense-entries/<id>/link` `{version, source: card | bank, txnId, by}` links one (refused when the entry or the charge is linked already; 409 when it changed since) and answers with the ledger's book. It returns:
- the tax items with what each paid in the year (and its deductible part);
- every payment that counts toward the year, with its tax year and quarter (estimated payments by quarter, January → Q4 of the year before; refunds toward the year before; by-hand moves win);
- the summary: expenses paid and deductible, payments by jurisdiction and quarter, real estate taxes, refunds, tax savings in and out;
- the registers that start after the year does;
- the cash-ledger lines.

It reads the registers by target account, ledger line or card name, not the spending view. `PUT /spending/tax/items/<id>` (id 0 adds; `{payeeId | ledgerLineId | namePattern, label, section expense / payment / real_estate / refund / savings, taxCategory, jurisdiction, deductibleShare, quarterly, notes, active}`), `DELETE /spending/tax/items/<id>` and `PUT /spending/tax/assign/<source>/<entryId>` (`{taxYear, quarter, note}`; no taxYear undoes the move) change it and answer with the report. `PUT /spending/change/entry/<source>/<id>` `{author, category, driver}` and `PUT /spending/change/trigger/<id>` `{author, category, kind}` apply a family-page change (V041): an entry's tag, or the trigger's fields. Each also adds a `change` note with what it replaced. `POST /spending/feedback/<id>/undo` puts it back and marks the note Not planned, "Undone.". `PUT /spending/feedback/<id>` `{status (new / seen / planned / done / declined), reply, by}` are the notes from the family's read-only web page (V039, `Services/spending-web`), newest first; answering one sets who answered and when. A tag (`{category, driver, memberId, event, notes}`; nothing set removes it) answers with the entry as now resolved; with `merge: true` only the fields sent change and the rest of the entry's own tag stays (Entries' Set Category and Set Driver on several entries). Drivers: inflation, family_growth, new_activity, lifecycle, preference, lifestyle (V045), one_time, taxes (V044) |

```bash
python3 Services/mxservices.py start accounts     # or: python3 accounts_service.py --port 8774
curl -s 'http://127.0.0.1:8774/securities?q=AGG&kind=bonds'
```

Needs `psycopg2`; the connection comes from SRM's own configuration (`MxDataHUB/SRM/README.md`). The earnings
endpoints don't touch the database (the fundamentals endpoint reads it when it can): they use SRM's FMP key (`FMP_API_KEY`, Keychain `SRM-api` / `fmp`, or
`config.local.json`), so the sandboxed MxAcctMGR needs no key of its own. Answers are cached in the process (15
minutes for recent weeks, 12 hours for older ones). Listens on
127.0.0.1 only; `--token` (or `MXJOBS_SERVICE_TOKEN`) requires `Authorization: Bearer <token>`.
